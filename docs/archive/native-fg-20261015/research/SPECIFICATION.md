# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
# GFG EXTREME — NATIVE FRAME GENERATION ENGINE

**Проект:** GFG Extreme
**Направление:** Reverse Engineering / GPU Compute / Vulkan / Frame Generation
**Приоритет:** P0 — критический
**Исполнитель:** AI Engineering Agent
**Репозиторий:** `wavessevaw/GFG-Extreme`
**Целевая платформа:** Steam Deck OLED / LCD, SteamOS, AMD RDNA 2
**Статус:** исследование и разработка независимого генератора кадров

---

# 1. ОСНОВНАЯ ЦЕЛЬ

Разработать для GFG Extreme собственный высокопроизводительный генератор промежуточных кадров, не зависящий от Lossless Scaling.

В настоящий момент разработка собственного генератора привела к увеличению вычислительной стоимости кадров. Последовательные попытки создания новых алгоритмов не позволили добиться необходимого соотношения производительности, качества и энергопотребления.

**Принято решение изменить методологию разработки.**

Вместо дальнейшего экспериментального создания алгоритмов с нуля необходимо провести глубокий реверс-инжиниринг двух существующих программных решений:

1. **Lossless Scaling / LSFG** — оригинальная технология генерации кадров.
2. **MAKO Renderer** — реализация исполнения моделей LSFG в Vulkan/Linux и интеграции с графическим конвейером.

Необходимо исследовать реальные принципы работы, архитектурные решения, алгоритмы, шейдеры, управление ресурсами GPU, обработку движения, синхронизацию и стоимость вычислений.

На основании исследования создать самостоятельный движок:

**GFG Native Frame Generation Engine (GFG Native FG).**

Новый движок должен:

- Работать без установленного Lossless Scaling.
- Не использовать `Lossless.dll` во время исполнения.
- Не требовать закрытых моделей LSFG.
- Выполнять генерацию кадров средствами Vulkan Compute.
- Обеспечивать сопоставимое с LSFG качество изображения.
- Стремиться к меньшей вычислительной стоимости, чем MAKO + LSFG.
- Сохранять производительность исходной игры.
- Полноценно интегрироваться в существующую архитектуру GFG Extreme.
- Быть пригодным для самостоятельного распространения.

**Главная задача — не придумать очередной генератор кадров, а сначала разобраться, как устроены уже работающие технологии, после чего создать собственную, более эффективную реализацию.**

Стоимость вычислений LSFG.

Ожидание, семафоры, barriers и задержки GPU-очередей.

Подготовка и выдача изображения в Gamescope.

## 5.2. Особое внимание LMC

В текущей экспериментальной архитектуре LMC используется разделённая обработка движения:

`GPU Analysis → CPU Readback → CPU Motion Fitting → GPU Upload → Synthesis`

Проверить, насколько оправдана эта схема.

Необходимо измерить:

- задержку чтения результатов;
- ожидания timeline semaphore;
- стоимость CPU fitting;
- задержки второй отправки команд;
- время получения готового motion field;
- количество GPU compute passes;
- объём промежуточных буферов;
- нагрузку на CPU;
- влияние на GPU queue;
- полное время до готовности сгенерированного изображения.

Рассмотреть альтернативы:

- GPU-only motion fitting;
- упрощённая глобальная модель движения;
- асинхронный CPU fitting;
- использование модели предыдущей пары;
- частичное обновление модели;
- уменьшение количества синхронизаций;
- объединение compute passes.

Ни одну из альтернатив не считать автоматически лучшей без измерений.

# 6. ЭТАП IV — ПРОЕКТИРОВАНИЕ GFG NATIVE FG

**Цель:** на основе доказанных результатов исследования спроектировать независимый генератор кадров.

## 6.1. Основная архитектура

Приоритетная модель:

**Один анализ движения для пары реальных кадров → повторное использование результатов → создание нескольких промежуточных кадров.**

Проектировать конвейер с минимизацией повторных операций.

Предполагаемая схема:

`Source A + Source B`

↓

`Preprocessing`

↓

`Motion Analysis`

↓

`Motion / Confidence / Occlusion Data`

↓

`Shared Temporal Representation`

↓

`Synthesis(t1), Synthesis(t2), ...`

↓

`Generated Images`

↓

`Presentation`

Структура является исходной архитектурной гипотезой и может быть изменена после завершения реверс-инжиниринга.

## 6.2. Исследуемые алгоритмы

Рассмотреть:

- hierarchical optical flow;
- bidirectional motion estimation;
- global motion compensation;
- layered motion compensation;
- block matching;
- temporal motion reuse;
- occlusion-aware interpolation;
- confidence-guided synthesis;
- adaptive refinement;
- selective high-quality processing;
- static-region reuse;
- HUD preservation;
- scene-cut detection.

Выбор алгоритмов осуществлять на основании измеренной эффективности.

## 6.3. GPU-оптимизация

Приоритет: AMD RDNA 2.

Исследовать:

- FP16;
- wave32 / wave64;
- subgroup operations;
- LDS/shared memory;
- register pressure;
- occupancy;
- texture-cache locality;
- память VRAM;
- GPU bandwidth;
- fused compute passes;
- indirect dispatch;
- persistent resources;
- asynchronous compute;
- оптимальную структуру workgroups.

Не считать уменьшение количества инструкций или texture fetches автоматическим улучшением.

Критерий — измеренное сокращение полной стоимости генерации.

## 6.4. Работа с разрешением

Исследовать варианты:

- полный размер исходного изображения;
- уменьшенное разрешение оценки движения;
- разные разрешения анализа и синтеза;
- локальная детализация сложных областей;
- восстановление деталей в финальном изображении.

Отдельно проверить эффективность на 1280×800.

Не допускать незаметного ухудшения HUD и текста.

## 6.5. Классы вычислительной сложности

Предусмотреть возможность разделения регионов:

**REUSE:** дешёвое воспроизведение подтверждённо статичного содержимого.

**LIGHT:** интерполяция с уже вычисленным полем движения.

**FULL:** дополнительный анализ сложного движения, перекрытий и локальных ошибок.

Границы классов не должны создавать швы, мерцание или пространственную нестабильность.

Классификация должна окупать собственную стоимость.

## 6.6. Режимы качества

Предусмотреть:

- Performance;
- Balanced;
- Quality.

По возможности использовать общий motion analysis и общие промежуточные данные для всех режимов.

Не создавать полностью независимые вычислительные графы без необходимости.

## 6.7. Управление GPU-бюджетом

Создать Frame Cost Controller.

Контроллер должен учитывать:

- стоимость анализа пары кадров;
- стоимость каждого синтетического кадра;
- фактическую загрузку GPU;
- требуемый output cadence;
- производительность исходной игры;
- количество пропущенных кадров;
- доступный вычислительный бюджет.

При перегрузке он должен выбирать более дешёвый режим или уменьшать число генерируемых кадров.

Не допускать бесконтрольного накопления очереди.

При недостаточном бюджете приоритет имеют настоящие кадры игры.

# 7. ЭТАП V — РЕАЛИЗАЦИЯ ДВИЖКА

## 7.1. Технические требования

GFG Native FG должен:

1. Работать через Vulkan Compute.
2. Поддерживать Steam Deck OLED и LCD.
3. Работать на AMD RDNA 2.
4. Использовать самостоятельные шейдеры и алгоритмы.
5. Не загружать модели из `Lossless.dll`.
6. Не обращаться к установленному Lossless Scaling.
7. Поддерживать генерацию 2× и 3×.
8. Предусматривать расширение до более высоких множителей.
9. Использовать аппаратную синхронизацию Vulkan.
10. Работать с существующим renderer contract GFG.
11. Передавать диагностику в Governor/Autopilot.
12. Сохранять корректность работы после пересоздания swapchain.

## 7.2. Управление памятью

Не допускать:

- постоянных выделений GPU-памяти на каждый кадр;
- ненужного копирования изображений;
- постоянных CPU readback;
- блокирующих CPU/GPU переходов;
- избыточных промежуточных изображений;
- неограниченного роста GPU-очереди;
- утечек ресурсов;
- неконтролируемого увеличения VRAM.

Ресурсы должны по возможности создаваться при инициализации контекста и повторно использоваться.

## 7.3. Синхронизация

Обеспечить:

- корректную работу timeline semaphores;
- независимость вычислительной очереди от основного рендера в допустимых пределах;
- правильные ownership transfers;
- обработку отказов Vulkan;
- bounded waits;
- безопасное завершение контекста;
- корректное поведение при suspend/resume;
- восстановление после ошибок.

При отказе генератора игра должна сохранять возможность продолжить работу без синтетических кадров.

## 7.4. Обязательная независимость

Итоговый генератор должен запускаться на Steam Deck без Lossless Scaling.

Это обязательный приёмочный тест.

LSFG допускается использовать только в исследовательском стенде или как дополнительный совместимый backend при отдельной законной установке. Он не может быть обязательным fallback для самостоятельного GFG Native FG.

Основной аварийный режим: обычный вывод настоящих кадров.

# 8. ЭТАП VI — ИЗМЕРЕНИЕ ПОЛНОЙ СТОИМОСТИ

Измерять не только время отдельного шейдера, но весь вычислительный конвейер.

Для пары кадров:

`T_work = T_input + T_analysis + N × T_synthesis + T_transport`

Где N — количество синтетических изображений.

Отдельно измерять критический путь до готовности и вывода изображения, учитывая перекрытие асинхронных операций.

Фиксировать:

- GPU analysis time;
- GPU synthesis time;
- GPU transport time;
- synchronization waits;
- CPU cost;
- p50/p95/p99;
- real FPS;
- output FPS;
- фактически представленные изображения;
- энергопотребление;
- GPU utilization;
- GPU clock;
- VRAM;
- температуру;
- end-to-end latency там, где она может быть достоверно измерена.

**Особое требование:** оптимизация считается успешной только тогда, когда она улучшает итоговую работу системы, а не отдельный диагностический показатель.

# 10. ЦЕЛЕВЫЕ ПОКАЗАТЕЛИ

## 10.1. Производительность

Целевой ориентир:

**До 2 мс GPU на один синтетический кадр при 1280×800**, с отдельным измерением стоимости анализа пары кадров.

Это инженерная цель, достижимость которой необходимо проверить.

Необходимо стремиться к снижению вычислительной стоимости не менее чем на 20% относительно MAKO + LSFG в сопоставимом режиме и на одинаковом оборудовании.

## 10.2. Качество

Цель: качество не хуже выбранного эталонного профиля LSFG по совокупности визуальных и временных метрик.

Недопустимы:

- выраженный ghosting;
- разрушение текста;
- сильное мерцание;
- заметные швы;
- нестабильные motion fields;
- повторяющиеся неправильные изображения;
- некорректная обработка смены сцены.

## 10.3. Системная эффективность

Новый движок должен стремиться:

- уменьшить GPU time;
- снизить энергопотребление;
- сохранить настоящий FPS;
- обеспечить стабильный output cadence;
- не увеличивать необоснованно задержку;
- сохранять работоспособность при ограниченном TDP.

При конфликте между увеличением числа синтетических кадров и сохранением настоящих кадров приоритет отдаётся настоящим.
